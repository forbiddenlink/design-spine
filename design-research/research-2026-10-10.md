# Design Spine: competitor research and improvement opportunities

> Research snapshot taken before implementation. See [implementation and verification](implementation-2026-10-10.md) for current completion status.
Research date: October 10, 2026. Current source: `main`, commit `17528f9`.
Scope: Design Spine itself, confirmed by Liz. Research and proposals; no product implementation.

## Recommendation

Make Design Spine an excellent local visual review tool for developers and designers working on their own applications. Concentrate on trustworthy captures, visible coverage, and fast, precise inspection. Retain the existing warm paper/ink/orange identity while making screenshots occupy more of the workspace.

The opportunity is not a longer feature list. It is answering four questions clearly: What did we capture? What did we miss? What changed? What did a person actually approve?

This is a recommendation inferred from the current workflow and the sources below, not evidence of market demand. There are no user interviews, adoption figures, authenticated competitor trials, or independent design ratings in this research.

## Competitors and similar repositories

| Source | Verified documented pattern | Implication for Design Spine |
| --- | --- | --- |
| [Chromatic review](https://www.chromatic.com/docs/review/) | Separates visual tests from review of intentional changes; links changesets to PRs; tracks discussions and review tasks. | Separate machine evidence, human decisions, and baseline promotion visibly. A completed review need not mean the baseline has changed. |
| [Argos overview](https://argos-ci.com/docs) and [repository](https://github.com/argos-ci/argos) | Screenshot pipeline, baseline comparison, PR review; supports other file comparisons. Repository is MIT licensed; managed cloud is the supported offering, with a substantial infrastructure stack. | Study review concepts and source patterns selectively. Do not replace this small local tool with a self-hosted Argos stack. |
| [Argos flake changelog](https://argos-ci.com/changelog/2026-03-10-auto-ignore-flaky-changes) | Documents automatic ignoring after flaky-change detection, with configurable recurrence. | Noise control matters. For Spine, first expose repeat-capture instability; do not silently adopt automatic ignoring or approval. |
| [Percy regions](https://www.browserstack.com/docs/percy/set-regions/define-regions) | Supports drawn/DOM-linked regions, sensitivity settings, and inspection of ignored differences. | Add deliberate, visible masking only after stabilizing inputs. Keep the raw screenshot and show exactly which areas were excluded. |
| [BackstopJS](https://github.com/garris/BackstopJS) | Ready selectors/events, pre/post scripts, clicks/hovers, selector captures, configurable viewports, local reports, selective approval. | The most directly useful source for capture readiness and genuine interactive states. Spine currently has much less state execution. |
| [Lost Pixel](https://github.com/lost-pixel/lost-pixel/blob/main/README.md) | Storybook/Ladle/Histoire/pages/custom-shot inputs; documents retries and masking. Distinguishes standalone engine from platform review features. | An image-import adapter can extend Spine without building a new capture engine for every framework. Storybook support is a later option. |
| [reg-suit](https://github.com/reg-viz/reg-suit/blob/master/README.md) | CLI image comparison with separate baseline-key, storage, and notification plugins; Git-aware baseline selection. | Borrow explicit baseline identity and separation of concerns. Cloud storage and notification plugins are not necessary for the local product. |
| [Loki](https://loki.js.org/) | Storybook visual regression with reproducibility as a stated goal and multiple capture environments. | Stable capture environments matter more than a prettier report. This source establishes documented scope, not current maintenance health. |
| [Playwright screenshots](https://playwright.dev/docs/test-snapshots) and [assertion API](https://playwright.dev/docs/api/class-pageassertions#page-assertions-to-have-screenshot-1) | Screenshot assertions wait for two consecutive matching captures; offer masking and screenshot policies. Assertions belong to Playwright Test. | Spine calls the browser screenshot API directly. It does not inherit this assertion stability behavior simply by depending on Playwright. Adapt the principle rather than assuming the assertion can be dropped into the CLI. |
| [Playwright trace viewer](https://playwright.dev/docs/trace-viewer) | Connects actions, before/after DOM snapshots, source, screenshots, and logs. | Link capture failures to diagnostic evidence. Start with bounded failure artifacts rather than tracing every successful page. |

These are references to investigate, not dependencies to install wholesale. This pass did not audit their internals, run their software, compare prices, or establish maintenance/security suitability for adoption. Any code reuse needs file-level license and implementation review.

## Current gaps grounded in source

1. **Coverage disappears from the review denominator.** `todo` states are skipped, and the stored run contains captured tiles rather than the planned/skipped matrix. A reviewer can finish all captured tiles while substantial UI states remain untested. [Job planning](/Volumes/LizsDisk/design-spine/src/lib/capture.ts:25), [run record](/Volumes/LizsDisk/design-spine/src/lib/capture.ts:319).
2. **State setup is prose, not execution.** The manifest includes a `setup` string; route generation populates instructions, but capture uses storage state and query parameters without executing setup text. Removing `todo` does not by itself create a loading/error/empty state. [State definition](/Volumes/LizsDisk/design-spine/src/lib/types.ts:10), [generated setup instructions](/Volumes/LizsDisk/design-spine/src/lib/routes.ts:67), [capture sequence](/Volumes/LizsDisk/design-spine/src/lib/capture.ts:229).
3. **Readiness is generic.** Capture waits for load, a bounded network-idle attempt, fixed delays, scrolling, fonts, and image decoding. It has no per-state ready selector or bounded repeat-image stability check. Asset waiting already exists and should be preserved. [Readiness](/Volumes/LizsDisk/design-spine/src/lib/capture.ts:178), [sequence](/Volumes/LizsDisk/design-spine/src/lib/capture.ts:238).
4. **Capture policy is narrow and partly implicit.** Chromium only; width determines hardcoded height; scale is 1; reduced motion is fixed. Locale/timezone, device profile, engine, and explicit animation behavior are not in the manifest model. [Context](/Volumes/LizsDisk/design-spine/src/lib/capture.ts:222), [launch](/Volumes/LizsDisk/design-spine/src/lib/capture.ts:300).
5. **Run provenance is incomplete.** Runs store identity, timestamps, base URL, and tiles, but not source commit, dirty-source state, browser/runtime versions, or manifest hash. Baseline run and approval time are already exposed in comparison, so this is an extension rather than a missing provenance feature from scratch. [Run type](/Volumes/LizsDisk/design-spine/src/lib/types.ts:61), [existing provenance](/Volumes/LizsDisk/design-spine/src/lib/comparison.ts:10).
6. **Gate policy needs to be explicit.** Missing baselines report `new` without incrementing failures. The diff command does not make rejection or pending review a release condition, and comparisons iterate the current run rather than reporting expected tiles absent from it. These are policy gaps for a strict release gate, not proof that the current documented pixel-diff behavior is broken. [Diff loop](/Volumes/LizsDisk/design-spine/src/cli.ts:225).
7. **Manifest loading trusts a cast.** JSON parsing is cast to `Manifest`; CLI numeric validation and filename collision detection exist, but they are not manifest schema validation. [Loader](/Volumes/LizsDisk/design-spine/src/lib/capture.ts:331).
8. **Change size is reduced to a whole-image ratio.** The comparison has two different concepts: per-pixel color sensitivity and the permitted ratio of changed pixels. Large pages can dilute a small but consequential change; dimensions changed are correctly treated separately. [Comparator](/Volumes/LizsDisk/design-spine/src/lib/diff.ts:13).
9. **Notes lack spatial anchors.** A review entry has decision, note, and update time. Blank-region coordinates are captured, but human notes and critique locations are not normalized image regions. [Review type](/Volumes/LizsDisk/design-spine/src/lib/types.ts:71), [critique shape](/Volumes/LizsDisk/design-spine/src/lib/types.ts:81).
10. **Token lint is a heuristic.** It counts selected arbitrary-value text patterns. It does not prove token use, consistency, or good design. A deliberate value can be legitimate. [Lint patterns](/Volumes/LizsDisk/design-spine/src/lib/lint.ts:11).

## Prioritized backlog

P0 means the next meaningful product scope; P1 follows the foundation; P2 is conditional. These are proposed priorities, not approved implementation specifications. New persistent fields should use a versioned, backward-compatible format rather than rewriting old evidence.

| Priority | Add or improve | Acceptance evidence |
| --- | --- | --- |
| P0 | Coverage ledger: planned, captured, skipped, failed, and intentionally excluded states | A run with 8 reviewed captures and 4 unfinished states explicitly reports both numbers; unfinished coverage cannot become a green complete result. |
| P0 | Manifest validation and a preflight/doctor command | Invalid widths, theme methods, missing state files, unresolved parameters, and malformed entries produce precise errors before launching a browser; no session-file contents printed. |
| P0 | Per-state readiness conditions | A delayed fixture waits for the intended element; timeout reports the condition and elapsed bound. Fixed sleeps are not the sole readiness contract. |
| P0 | Executable state recipes | Explicit, bounded click/fill/hover/wait/network-fixture steps generate demonstrably different ideal/empty/error/loading screenshots. Existing `setup` prose remains documentation. Do not evaluate it as code. |
| P0 | Strict gate policy | An exit-code matrix covers changed, new, absent expected capture, failed capture, pending, and rejected; keep a compatibility mode for existing pixel-only users. Human approval never changes automatically. |
| P0 | Compact review layout | At 1280×800, the first useful screenshot area is visible without scrolling. Preserve labels, touch targets, readable status, and keyboard order; test at 390px and 200% zoom. |
| P0 | Documented capture provenance | Record commit/dirty state, browser/runtime, manifest hash, dimensions, and policy. Unknown provenance on old runs is clearly unknown; comparison warns about incompatible environments. |
| P1 | Repeat-capture stability diagnostic | A static fixture settles; an unstable fixture is marked unstable after a bounded retry budget. Keep evidence of instability rather than raising the global threshold. |
| P1 | Deliberate animation/time/data policy | Motion fixture documents preserve vs finish/reset outcomes; frozen clock/data is opt-in and recorded. Existing baselines are not silently reinterpreted. |
| P1 | Regional diff navigation | Small changes near the bottom of a long page produce regions and next/previous jumps. Include changed-pixel count as well as page ratio; test anti-alias noise and size changes. |
| P1 | Synchronized comparison and optional overlay | A reviewer can inspect the same coordinate in two long captures. Keyboard-operable opacity/wipe is optional; split/difference modes remain available. |
| P1 | Image-anchored review notes | Store coordinates in native-image units with screenshot identity/hash. Anchors remain correct across fit/actual sizing and clearly stale when evidence changes. |
| P1 | Visible masks with reasons | Dynamic clock can be excluded without concealing a nearby button regression. Exclusions appear in UI/export; raw evidence is retained. |
| P1 | Run switcher and local history | Switch between two runs without losing failed drafts; identify baseline sources and use stable tile deep links. Existing CLI run selection stays usable. |
| P1 | Better queues and route progress | Show failed captures, changed evidence, new evidence, and pending decisions separately; route index reports remaining review. Sorting is deterministic and does not lose focus. |
| P1 | Portable local report | Export a self-contained or relative-asset HTML bundle plus machine JSON; open it offline on another machine with no review server or external requests. Make read-only status explicit. |
| P1 | First-run guidance | From an empty project, produce a validated manifest, one capture, one review decision, and one explicit baseline promotion. Explain unfinished states without pretending they are configured. |
| P1 | Failure diagnostics | Attach bounded trace/network/readiness evidence to failures using synthetic test data. Omit credential-bearing headers and state files from exported artifacts. |
| P1 | Accessibility checks on captured applications | Add optional axe results and keyboard-state captures. Keep violations, incomplete checks, and human findings separate; zero automated violations is not a conformance certificate. [Playwright guidance](https://playwright.dev/docs/accessibility-testing). |
| P1 | Distribution and memory validation | Build from current source, run from outside the checkout, verify worker/assets resolution; measure multi-hour comparison and idle RSS before claiming standalone readiness or bounded memory. |
| P2 | Image import / Playwright and Storybook adapters | Imported images retain original identity and provenance; adapter output enters the same review workflow. Start with one adapter, not a plugin framework. |
| P2 | Locale, RTL, device, and browser profiles | Add one real use case at a time; browser/environment-specific baselines prevent accidental cross-engine comparison. |
| P2 | Design-reference comparison | Keep Figma/reference intent separate from a regression baseline; label design-to-build differences and align dimensions explicitly. Never imply pixel identity proves UX quality. |
| P2 | Explainable token checks | Report concrete offending file/line and configured rule; support documented exceptions. Do not label arbitrary-value counts a design-quality score. |

## Visual research: what transfers, and what does not

### Observed problem in Spine

At the approximately 1260×700 desktop browser view inspected, current Spine's heading, summary, filters, comparison status, and reserved save-status space occupied the first screen; no screenshot preview was visible. The earlier October 8 image showed screenshot tops sooner, but it predates the added controls. This is why current inspection matters.

The viewer is more focused: compact route/state metadata at top, image canvas in the middle, decision bar below. This is worth preserving. The blank demo screenshot is intentionally plain and is not evidence that the review tool needs decorative imagery.

Source areas: [intro and summary spacing](/Volumes/LizsDisk/design-spine/src/ui/index.html:52), [toolbar](/Volumes/LizsDisk/design-spine/src/ui/index.html:69), [status rows](/Volumes/LizsDisk/design-spine/src/ui/index.html:214). Reserve enough space to prevent lost clicks, but investigate a fixed status location or compact status rail instead of simply deleting the previously verified layout-stability protection.

### Three directions to explore with Claude

1. **Refined review workspace — recommended.** Keep the existing identity. Collapse the large intro into run context; make progress compact; show screenshots early; use a persistent inspector for decisions, diagnostics, and notes. Lowest conceptual disruption, with the clearest connection to the current product.
2. **Change-review inbox.** Dense list of changed/failed/new tiles with route groups; opening a row prioritizes comparison. Strong for repeated release review, weaker for first-baseline creation and browsing all screens. Prototype as an alternate mode, not an immediate replacement.
3. **Reference-board canvas.** Large screenshot arrangements, pinned details, and visual references. Useful for occasional art direction; weaker for coverage, keyboard order, and reproducible sign-off. Defer a standalone canvas until a repeated need is demonstrated.

Use task performance to choose. Give the same reviewer the same synthetic set: locate a mobile overflow, find a tiny lower-page change, reject with a useful note, recover a failed save, and explain remaining coverage. Record time, wrong decisions, navigation effort, and whether the correct coordinate was inspected. Compare with the current tool. Do not score taste alone.

### Avoiding a generic generated appearance

This is a craft objective, not something a detector can certify. Propose these constraints for the designer:

- Let actual screenshots provide the visual richness. No generated illustrations are needed in the workspace.
- Retain one recognizable identity detail, consistent spacing, and clear type hierarchy. A new font or unusual effect must solve a specific problem.
- Remove repeated introductory slogans from the daily workflow. Use meaningful run/route/state context in that space.
- Do not give every count, action, and status equal visual weight. Evidence and the next decision should dominate.
- Design deliberately for long URLs, long pages, no baseline, dimension mismatch, loading/error states, dark captures inside a light UI, and unsaved changes.
- Keep saved/pending/failed, changed/within-threshold, and approved/rejected visually distinct. Color must not be the only signal.
- Use motion to explain a local state transition, respect reduced motion, and avoid moving image evidence during inspection.
- Review polished screens with real permitted content after synthetic edge cases; neither beautiful mock data nor an automated accessibility score establishes quality.

## What to create

Create a compact evidence board with each reference linked to a specific decision; two competing workspace prototypes; a state inventory; a versioned capture/coverage specification; synthetic readiness/instability/long-page fixtures; and a short product positioning/demo brief if distribution becomes a goal.

Do not start a marketing site simply because this is called a site. This repo currently delivers a local review application. If a public page is later wanted, lead with a real capture → inspect → decision demonstration, explain the local workflow, list honest limits, and offer a reproducible demo. Testimonials, usage statistics, pricing tiers, and enterprise claims require actual evidence.

## Recommended sequence

1. Specify and verify coverage/preflight/gate behavior. Add provenance with backward compatibility. Confirm that the tool cannot present incomplete evidence as complete review.
2. Add readiness and one executable state recipe. Verify with synthetic delayed/error/loading examples before expanding the recipe vocabulary.
3. Have Claude prototype directions 1 and 2 using the current UI and the same test set. Choose based on inspection tasks and visual judgment together.
4. Implement the selected compact layout, regional navigation, and synchronized comparison. Preserve all existing draft, save, focus, and explicit baseline protections.
5. Add anchored notes and portable reports, then verify packaging, memory, keyboard/screen-reader behavior, and browsers/devices actually supported.

Do not lead with hosted accounts, billing, social feeds, more model providers, autonomous approval, bulk baseline promotion, or a framework rewrite. None addresses the strongest observed gaps. A better tool is the one that makes evidence reliable and decisions clear.

## Remaining uncertainty

No user testing establishes which layout wins. No authenticated competitor workflow was exercised. Current production use, target distribution model, and desired team collaboration are unknown. Previous reports leave manual VoiceOver, idle resident memory, physical-device behavior, and standalone distribution incompletely established; current worker release and build code exist, so investigate them rather than assuming the earlier state still holds. The backlog includes these as verification tasks, not newly reproduced failures.

This report is a researched proposal. It does not claim Design Spine is the best product in the category, that its current design is AI-generated, or that a particular aesthetic guarantees quality.
